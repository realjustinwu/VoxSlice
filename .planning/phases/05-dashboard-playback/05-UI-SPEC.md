# Phase 5 — UI Design Contract

> Visual and interaction contract for Dashboard + Playback. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (native macOS) |
| Preset | not applicable |
| Component library | SwiftUI + AppKit |
| Icon library | SF Symbols 5 |
| Font | SF Pro (system default) |

**Rationale:** Native macOS Swift/SwiftUI application. Follows Apple Human Interface Guidelines. Continues the design system established in Phase 1 (01-UI-SPEC.md) and inherited by Phases 3 (03-UI-SPEC.md) and 4 (04-UI-SPEC.md). No web-based design system applies.

## Spacing Scale

Inherited from Phase 1 UI-SPEC. All values follow Apple's 8-point grid.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline label spacing, segment block internal spacing |
| sm | 8px | Compact element spacing, within-group padding, copy button gaps, player control gaps |
| md | 16px | Default element spacing, sidebar row internal padding, transcript segment gaps, analysis section padding |
| lg | 24px | Section padding, detail view top-level section spacing, player section padding |
| xl | 32px | Window-level content padding, sidebar padding |
| 2xl | 48px | Major section breaks, empty state vertical spacing |
| 3xl | 64px | Page-level spacing |

Exceptions: none

## Typography

Inherited from Phase 1 UI-SPEC. Uses SF Pro via SwiftUI system font APIs.

| Role | Size | Weight | SwiftUI API | Line Height |
|------|------|--------|-------------|-------------|
| Body | 13pt | .regular (400) | `.body` or `Font.system(size: 13)` | 1.38 (default) |

**Additional typography for this phase:**

| Role | Size | Weight | SwiftUI API | Usage |
|------|------|--------|-------------|-------|
| Timestamp | 11pt | .regular (400) | `.caption` or `Font.system(size: 11)` | Transcript segment timestamps `[MM:SS - MM:SS]`, player time display |

### RecordingHistoryService (New Service)

New `@Observable` service to load and manage recording history from disk.

**Responsibilities:**
- Scan recordings/ directory for `*.json` metadata files
- Decode each as RecordingInfo
- For each recording, check for matching transcript in transcripts/ (by timestamp prefix)
- For each recording, check for matching analysis in analysis/ (by timestamp prefix)
- Build in-memory list of `RecordingHistoryItem` (RecordingInfo + optional TranscriptInfo + optional AnalysisResult)
- Compute processing status from file existence

**Processing status enum:**
```swift
enum ProcessingStatus {
    case new           // Recording metadata exists, no transcript
    case transcribing  // Currently being transcribed (inferred from coordinator state)
    case transcribed   // Transcript exists, no analysis
    case analyzing     // Currently being analyzed (inferred from coordinator state)
    case completed     // Transcript + analysis both exist
    case failed        // Transcription or analysis failed (inferred from error state)
}
```

**Data model:**
```swift
struct RecordingHistoryItem: Identifiable {
    let id: UUID                    // Same as RecordingInfo.id
    let recording: RecordingInfo
    let transcript: TranscriptInfo?
    let analysis: AnalysisResult?
    let status: ProcessingStatus
    var displayTitle: String        // First topic name or date/time fallback
    var displaySummary: String?     // TL;DR if available
}
```

## Interaction Patterns

### Open Dashboard Flow

```
1. User clicks "Open Dashboard" in menu bar dropdown (or presses cmd+D)
2. Dashboard window opens (or is brought to front if already open)
3. Window position/size restored from UserDefaults
4. RecordingHistoryService loads recording list from disk
5. Sidebar populates with recording rows, newest first
6. No recording selected by default -- detail view shows placeholder
```

### Sidebar Selection Flow

```
1. User clicks a recording row in the sidebar
2. Row highlights with accent color
3. Detail view loads:
   a. Player loads the merged audio file (if available)
   b. Transcript segments render (if available, else "not available" state)
   c. Analysis sections render (if available, else "not available" state)
4. Player is in "Ready" state (play button enabled, slider at 0)
```

### Audio Playback Flow

Per D-13 through D-15.

```
1. User presses Play button in player controls
2. AVPlayer begins playback of merged audio file
3. Player slider tracks current time, updating every 0.25s
4. Current time label updates in real-time
5. As playback crosses segment boundaries:
   a. Previous segment highlight fades
   b. New segment highlight appears (accent color at 10% opacity + left border)
   c. ScrollView auto-scrolls to keep highlighted segment centered
6. User can:
   a. Click transcript segment -> audio seeks to segment.startTime
   b. Drag slider -> audio seeks to new position
   c. Press skip forward/back -> audio seeks +/- 15 seconds
   d. Change speed -> AVPlayer.rate updated immediately
   e. Press Pause -> playback pauses, highlight stays on current segment
7. When playback reaches end:
   a. Play button shows play icon again
   b. Highlight remains on last segment
   c. Slider stays at end position
```

### Search Flow

Per D-07.

```
1. User clicks search bar at top of sidebar
2. User types search query
3. After 300ms debounce, RecordingHistoryService filters recordings
4. Filter scope: display title, transcript segment text, analysis content
5. Sidebar list updates to show only matching recordings
6. If no matches: sidebar shows "No recordings match your search" empty state
7. User clears search -> all recordings shown again
```

### Copy Section Flow

Same pattern as Phase 4. Per-section copy buttons in the detail view.

```
1. User clicks copy button on any analysis section
2. Section text copied to NSPasteboard.general
3. Copy button flashes checkmark for 1.5 seconds
4. Text available for pasting
```

### Retry Flow (Detail View)

Per D-12: Retry buttons available in missing-data states within the detail view.

```
1. User sees "Transcript not available" or "Analysis not available"
2. User clicks "Retry Transcription" or "Retry Analysis"
3. System re-attempts from the beginning
4. Progress indicator shows in the relevant section
5. On success: Section populates with data
6. On failure: Error message with retry button persists
```

### Window Lifecycle

Per D-03.

```
1. Close button (red traffic light): Hides window, app stays running in menu bar
2. Reopen: "Open Dashboard" in menu bar or cmd+D
3. Position/size saved to UserDefaults on window move/resize
4. Position/size restored when window reopens
```

## Data Display Patterns

### RecordingHistoryItem Data Model

The primary data model consumed by dashboard views:

```
RecordingHistoryItem {
    id: UUID                        // Same as RecordingInfo.id
    recording: RecordingInfo {
        id: UUID
        startTime: Date
        endTime: Date?
        duration: TimeInterval
        micFilePath: String
        systemFilePath: String
        state: RecordingState
        // ... other fields
    }
    transcript: TranscriptInfo? {
        segments: [Segment] {
            id: UUID
            speaker: String
            startTime: Double       // seconds
            endTime: Double         // seconds
            text: String
        }
        speakers: [Speaker]
        language: String
        duration: Double
    }
    analysis: AnalysisResult? {
        summary: AnalysisSummary {
            tldr: String
            detailed: String
        }
        actionItems: [ActionItem]
        decisions: [String]
        topics: [Topic]
    }
    status: ProcessingStatus        // computed from file existence
    displayTitle: String            // first topic or date/time
    displaySummary: String?         // TL;DR or nil
}
```

### ProcessingStatus Computation

```
if recording matches current coordinator session AND (transcription or analysis is in progress):
    -> .transcribing / .analyzing
else if transcript JSON exists AND analysis MD exists:
    -> .completed (green dot)
else if transcript JSON exists AND no analysis MD:
    -> .transcribed (could trigger auto-analysis)
else if coordinator error state for this recording:
    -> .failed (red dot)
else:
    -> .new (gray dot)
```

### Audio File Strategy for Playback

Per D-13 and CONTEXT.md specifics: The merged audio file is currently temporary (created during transcription, deleted after). Playback requires one of:

1. **Persist merged file** (recommended): Save merged file in recordings/ alongside mic and system files. Simplest, lowest latency for playback.
2. **Re-merge on demand**: Re-create merged file when user plays audio. Higher latency, no extra disk usage.
3. **Play system audio only**: Fallback if merged file unavailable.

The planner decides implementation strategy. UI-SPEC requires: if merged audio is unavailable, show error message "Audio file not found. The recording may have been moved or deleted."

## Accessibility

- Sidebar recording rows use `.accessibilityElement(children: .combine)` with label "{title}, {date}, {duration}, {status}"
- Player controls have accessibility labels: Play/Pause, Skip forward 15 seconds, Skip back 15 seconds
- Timeline slider has `.accessibilityLabel("Playback position")` and `.accessibilityValue` updating with current time
- Speed buttons have `.accessibilityLabel("Playback speed {rate}")` and selected state announced
- Transcript segment blocks are `.accessibilityElement(children: .combine)` with label "{speaker}, {timestamp}, {text}"
- Currently-playing segment has `.accessibilityAddTraits(.isSelected)` for screen reader announcement
- Copy buttons have `.accessibilityLabel("Copy {section name}")` and `.accessibilityHint("Copy this section to clipboard")`
- Retry buttons have `.accessibilityHint("Retry the failed {transcription/analysis}")`
- Status dots use `.accessibilityLabel("Status: {status description}")` -- never color-only indicators
- Search field follows standard macOS accessibility with `.accessibilityLabel("Search recordings")`
- Dynamic Type: All typography uses SwiftUI semantic styles for user size overrides
